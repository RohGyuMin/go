당신은 이 저장소의 "AI 사무실 게임"(`web/game/`)의 **뇌**입니다. 아래 절차로 대기 중인 업무와
대화를 처리하세요. 규약 전문: `web/game/PROTOCOL.md`. 상태 타입: `web/lib/game.ts`.

## 1. 상태 읽기
`web/game/state.json`을 읽습니다. 없거나 비어 있으면 "처리할 게 없다"고 보고하고 종료합니다.

## 2. 대기 업무 처리 (`status === "todo"` 인 tasks)

**처리 순서 = 우선순위 · 의존성** (`web/lib/game.ts`의 `Priority`/`dependsOn` 참조):
- **선행 업무 확인**: task에 `dependsOn`이 있으면, 그 id들이 **모두 `done`일 때만** 착수한다.
  선행이 아직 안 끝났으면 그 task는 이번엔 건너뛰고 `todo`로 둔다(막힘 아님, 대기).
- **우선순위**: 착수 가능한 업무 중 `priority`가 `high` → `normal` → `low` 순으로 먼저 처리한다.
  (`priority` 없으면 `normal`로 취급.)

각 업무를 담당 캐릭터(`assignee`) 관점에서 실제로 처리합니다.

- **조사·설명·리뷰 등 코드 변경이 없는 업무**
  → 저장소를 읽고 실제로 답을 낸 뒤, task를 `done`, `result`에 한두 줄 요약.
- **코드를 실제로 바꾸는 업무** → **리뷰 게이트**를 따른다(자동 커밋 금지):
  1. 파일을 실제로 수정한다.
  2. task를 `status:"review"`, `result`에 무엇을 왜 바꿨는지, `changedFiles`에 바뀐 파일 경로.
  3. **커밋/PR은 하지 않는다.** 사람이 "커밋해"라고 할 때까지 기다린다.
- **막히면** `status:"blocked"`, `result`에 사유.
- 처리 중인 담당 agent의 `status`는 필요 시 `"working"`, 끝나면 `"idle"`로.

## 2.5. 병렬 처리 (멀티에이전트)
**착수 가능한**(선행 업무가 모두 `done`) 독립적인 `todo` 업무가 **2개 이상**이면
서브에이전트로 **동시에** 처리한다. 선행 대기 중인 업무는 팬아웃 대상에서 제외한다.

1. **시작 표시(1회 저장)**: 처리할 tasks를 `doing`, 담당 agents를 `status:"working"`으로 바꿔
   `state.json`을 한 번 저장한다. → 게임 맵에 여러 캐릭터가 동시에 "일하는 중"으로 보인다.
2. **팬아웃**: 각 업무를 **Agent 도구로 서브에이전트 하나씩** 띄워 동시에 수행한다.
   각 서브에이전트는 자기 업무만 하고 **결과(요약 / 변경파일 목록)를 반환**한다.
   ⚠️ 서브에이전트는 `state.json`을 직접 쓰지 않는다(동시 쓰기 경합 방지).
3. **병합(1회 저장)**: 모든 서브에이전트 결과를 모아 **한 번에** `state.json`에 반영한다
   (각 task를 `done`/`review`/`blocked`, `result`·`changedFiles` 채우고, agents를 `idle`로, `rev`+1).
4. **충돌 회피**: 서로 **같은 파일을 고치는** 업무는 병렬하지 말고 순차 처리한다.

> 조사/설명 업무는 병렬이 특히 안전하다. 코드 변경 업무는 리뷰 게이트(자동 커밋 금지)를 그대로 지킨다.

## 2.6. 승인된 업무 커밋/PR (`status === "approved"` 인 tasks)
사람이 게임 카드의 **"승인 (커밋/PR)"** 버튼을 눌렀거나 "커밋해"라고 말한 업무만 여기서 처리한다.
(리뷰 게이트를 통과한, 사람이 실제로 확인·승인한 코드 변경만 커밋된다.)

각 `approved` task에 대해:
1. `changedFiles`에 실제로 변경 사항이 남아 있는지 `git status`로 확인한다.
2. 담당 브랜치에서 변경 파일을 **실제로 커밋**한다.
   - 커밋 메시지 제목에 담당 캐릭터 이름과 업무 제목을 반영한다.
     예: `노바: 로그인 버튼 스타일 수정 (AI 사무실 업무 t3)`
   - 커밋 본문에 `result` 요약을 넣는다.
3. 원격에 push 하고, 열린 PR이 없으면 **draft PR을 만든다**(있으면 그 PR에 얹는다).
4. task를 `status:"done"`, `prUrl`에 PR(또는 커밋) 링크를 채운다. 담당 agent는 `idle`.
5. 커밋할 실제 변경이 없으면(이미 커밋됨 등) `done`으로 두고 `result`에 사유를 적는다.

> ⚠️ `state.json` 자체는 이 커밋에 **포함하지 않는다**(게임 상태와 코드 변경을 분리). 업무 코드 변경만 커밋한다.

## 3. 대화 응답
`chat[]`에서, 각 캐릭터별 마지막 메시지가 `from:"player"`이고 아직 답이 없으면,
그 캐릭터 톤(역할에 맞게)으로 `from:"agent"` 응답을 한 개 추가합니다. 짧고 자연스럽게.

## 4. 저장 & 보고
- `rev`를 현재 값 +1 로 올리고 `web/game/state.json`을 저장합니다(JSON 유효성 유지).
- 사용자에게 **무엇을 처리했는지 요약**합니다(완료 N건, 리뷰 대기 M건, 답변 K건).
- 리뷰 대기(코드 변경)가 있으면, 커밋하려면 "커밋해"라고 말하라고 안내합니다.

## 안전 규칙
- **커밋되는 코드는 오직 사람이 승인한(`approved`) 업무뿐입니다.** `todo`→`review`까지는 게임 상태
  (state.json) 쓰기만 자동이고, 실제 저장소 코드 변경은 `review`로 남겨 사람 확인을 받습니다.
- **루프(`/loop`)는 미승인 코드를 절대 커밋하지 않습니다.** 승인은 사람의 명시적 행동(버튼/발화)이므로,
  자동 루프가 스스로 `approved`를 만들지 않습니다. `approved` 커밋 단계(2.6)는 사람이 승인을 남긴
  업무에만 적용됩니다.
- 파괴적 작업(삭제·이동·외부 전송)은 자동 처리하지 말고 `blocked`로 두고 사람에게 물어봅니다.

## 자동 반복 (선택)
매번 지시하지 않으려면 로컬 Claude Code에서:
```
/loop 30s /process-game
```
30초마다 이 커맨드가 돌며 대기 업무를 집어갑니다. (중단: 루프 중지)
게임 화면은 2초 폴링이라 처리 결과가 곧 반영됩니다.
